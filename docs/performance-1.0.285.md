# 1.0.285 进入、开战与升阶卡顿优化

日期：2026-11-01。

## 已确认的开销

- 进入战斗预览会生成敌阵，并执行人口范围内最强阵容的静态搜索。备战武将和装备越多，候选阵容与配装评分越多。CPU 采样热点为属性计算和临时对象分配。
- 点击开始在主线程同步生成整场战报，然后保存、创建播放节点。`hero-skills.passive` 曾在高频查询时反复复制技能对象和数组。
- 合成、升阶与布阵后，战斗界面整体重绘，未变化武将也会重新创建和装配 Spine 组件。
- 菜单和备战过去沿用引擎默认 60 帧，持续绘制动画。

## 本次修改

1. 静态搜索独享有界评分缓存：只复用数值，保留队伍顺序、站位、装备归属、成长、倍率及所有其他属性；真实英雄和装备实例、搜索顺序、胜出候选不变。无需筛选阵容时直接计算，避免小阵容承担缓存序列化成本。缓存最多 2048 项，搜索完成即释放。
2. 被动查询直接扫描技能定义，避免构造完整临时技能数组；仍按当前技能列表读取，不引入可过期的技能缓存。
3. 连续备战重绘只保留已装配、同实例同身份同阶的骨骼身体。血条、触摸节点和装备显示重新建立。升阶、合成消耗、离开可见范围时释放旧身体；交战、结算和页面切换不跨生命周期复用。尚未装配的资源继续沿用原队列有效性检查。
4. 菜单/备战 30 帧，交战 60 帧；时间轴仍读取真实时间，战斗演算步长未改。策略集中在 `game/play/interaction-performance-config.js`。

存档提交、回滚、云同步、随机种子、奖励、技能数值和敌军难度规则未调整。

## 后续架构优化方向

仍存在同步整场演算和 UI 控件整体重建。下一步应先在真机分别记录点击响应、静态搜索、战斗演算、JSON 快照/同步写盘、骨骼装配和首帧时间，再按耗时占比推进：

- 将战斗演算封装为可恢复、可取消的分片任务，并保持随机数调用顺序与事件顺序完全一致。异步期间锁定操作、校验存档版本，仍以完整战果成功落盘作为播放前提；不可直接给现有同步事务回调加 `await`。
- 将战斗场景、上阵角色、手牌、顶部资源和弹窗拆成独立更新边界，由已提交的状态差异决定刷新范围；把本次骨骼复用发展为明确的组件生命周期，而非长期扩展整屏重绘中的特例。
- 在真机上验证长时间待机、普通/精英/Boss 连战、重复合成、翻页和切后台后的资源存活数，确认 CPU/GPU、纹理内存与温度趋势后，再决定画质档位和可见性动画策略。

尚未完成实体手机连续运行、发热及触摸手感验收；开发上传不等于审核或正式发布。
